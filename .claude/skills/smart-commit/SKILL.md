# Smart Commit

**Owns:** turning a working tree into commits on the current branch: what goes in, how
it is grouped, the message, the recovery when the pre-commit hook refuses, and the push
when the requested outcome needs it. **Does not own:** opening or updating the pull
request (`create-pr`); shipping an issue end to end (`shipping-issues`); what the hook
runs and why (`lefthook.yml`, `.claude/rules/gates.md`); the order of work that produces
a behavior change (`tdd`).

A user-level skill of the same name may also be installed. Inside this repository,
follow this one: it is the one that knows this hook.

`CLAUDE.md`'s "Security and human approval" sets the scope. Make the commits the
requested outcome needs on the task branch; push when that outcome includes a push, a
pull request, or shipping. A local commit request stays local. Never force-push, amend a
pushed commit, or push `main`.

## 1. State first

```bash
git branch --show-current
git status --short
git log --oneline -5
git diff --stat
git diff --cached --stat
```

- **On `main` or detached:** create a task branch before committing, preserving existing
  work. Changes reach `main` through a pull request.
- **A merge or rebase in progress:** `lefthook.yml` skips the hook for both, so nothing
  judges that commit. Run `pnpm check:quick` and `pnpm check:staged` yourself before
  concluding it.
- **Something already staged** that you did not stage: it is the requester's. Ask before
  folding it into a group or unstaging it.

## 2. Decide what stays out

The mechanical list (`.env*`, anything under `secrets/`, a key file, a credential in a
file's content) lives in `scripts/check-staged.mjs` and `scripts/lib/guard/`, and the
`check:staged` job refuses it at commit time. Do not restate it; what this step adds is
the judgment no pattern sees:

- A real key or token in an innocently named file: a fixture, a config, a log.
- Personal data in a fixture or a test expectation.
- Something the requester plainly did not mean to commit: a scratch file, a debug log, a
  build artifact `.gitignore` happens to miss, an editor's backup.

Judge a secret-shaped path by its name in `git status --short`, never by opening it.
Leave such a file unstaged and name it in the report.

## 3. Group

One commit per logical change: a reader of `git log` should be able to revert any one of
them without breaking another. Each is a Conventional Commit,
`<type>(<scope>): <summary>`: English, imperative, lower-case, no trailing period, under
72 characters. Take the type and scope the way `create-pr`'s "Title" does.

These always move together, in the same commit:

| Change                                                                    | Moves with                                      | Because                                                                                                                                                               |
| ------------------------------------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A dependency in a `package.json`, or a setting in `pnpm-workspace.yaml`   | `pnpm-lock.yaml`, regenerated by `pnpm install` | CI installs with `--frozen-lockfile`, which refuses a lockfile out of step with its manifest. `.claude/rules/dependencies.md` holds the sign-off a new package needs. |
| A behavior change in `packages/core/src/`, `apps/web/src/`, or `scripts/` | Its test, and any document the change owes      | A code-only commit lands untested behavior, and a later test can no longer be shown to have failed against it (`tdd`).                                                |

If all the changes are one logical change, one commit is right; three related one-line
edits are one commit, not three. When two logical changes touch the same file, stage
hunks with `git add -p <file>`, and read the `format` row below first.

## 4. Stage by name and commit

For each group, in dependency order:

```bash
git add <path> <path> ...
git diff --cached --stat
git commit -m "<type>(<scope>): <summary>"
```

- Stage by explicit path. Never `git add .`, `git add -A`, or `git commit -a`: each
  sweeps in whatever step 2 meant to leave out.
- Check `git diff --cached --stat` against the group before every commit; it is the last
  look before the hook takes its own.
- A longer body goes in a file outside the checkout, passed with `-F <file>`, so the
  shell expands nothing in it.
- The commit prints a `lefthook` summary. One that prints none ran no hook: run
  `pnpm hooks:install`, then judge that commit with `pnpm check:quick` and
  `pnpm check:staged` before going on.

## 5. When the hook refuses

Nothing was committed. Read which job failed, clear it by its row, re-stage what the fix
touched by name, then run the same `git commit` again: a new commit, never `--amend` of
an earlier one. Every job runs again, so a fix for one row can surface another.

| Job            | What the failure means                                                                                                                                                                                                                             | Clear it by                                                                                                                                                                                                  |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `format`       | Prettier could not parse a staged file. When it only reformats, it re-stages the file and the commit goes on. It re-stages the file whole, so on a partially staged file the unstaged hunks are swept into the commit.                             | Fix the syntax where it reports and re-stage. Before a partial stage, format the file (`pnpm exec prettier --write <file>`) and then stage the hunks, or stash the rest.                                     |
| `eslint`       | A lint violation in a staged file. The hook runs no autofix.                                                                                                                                                                                       | Fix the code where it reports, or run `pnpm fix` for what is fixable, and re-stage by name. Never a blanket `eslint-disable` and never a relaxed rule.                                                       |
| `typecheck`    | The whole workspace failed to type-check, not only the staged files: the error can sit in a file this commit does not touch, or in an untracked one.                                                                                               | Fix the type where it is. When the error lives in a change that belongs to a later group, set it aside (`git stash push --keep-index --include-untracked`), commit, and `git stash pop`. Never `@ts-ignore`. |
| `test:related` | A test reachable from the staged files failed.                                                                                                                                                                                                     | Fix the code. Change the test only when its expectation was wrong, and say so in the pull request. Never skip or delete it.                                                                                  |
| `check:staged` | A line starting `Blocked:` names a staged path that is secret-shaped (`looks like it holds secrets`, `looks like a private key file`) or staged content that `looks like it embeds` a credential; it names the path and the kind, never the value. | `git restore --staged <path>`, then tell the requester which path was refused and why, without opening it. A refusal you believe is wrong is a stop for a human to judge.                                    |
| any job        | pnpm refuses to run because `node_modules` is missing or no longer matches `pnpm-lock.yaml`.                                                                                                                                                       | `pnpm install --frozen-lockfile`.                                                                                                                                                                            |

Never `--no-verify` (or `-n`), never `LEFTHOOK=0` or another switch that turns the hook
or one of its jobs off, never an edit to `lefthook.yml`, `scripts/check-staged.mjs`, or
the installed hook to make this commit pass. Each removes the check rather than the
problem, and the secret gate goes down with everything else. `CLAUDE.md` holds the
prohibition; a refusal you cannot clear is a stop, reported with the job's output.

## 6. Push within the requested outcome

```bash
git push -u origin <branch>
```

- Push only the task branch, and only when the requested outcome includes publishing it.
- A rejection as non-fast-forward stops: the remote has commits this checkout lacks.
  Never force-push past it.
- A pull request is `create-pr`'s; return to that workflow when it called this skill.

## 7. Report

`git log --oneline origin/main..HEAD` (or the commits made, when there is no upstream),
whether anything was pushed and where, and every path left uncommitted with the reason.
